# P3 범위 확정

작성일: 2026-05-05
직전 기준: `docs/qa/p2-completion-summary-20260505.md`

## 1. P3 목표

P3의 목표는 P2에서 구현한 운영 화면, 리포트, 모니터링, PBX smoke gate를 실제 운영 전환 절차로 묶는 것이다.

P3는 새 기능 확장보다 운영 배포 안정성, 외부 장애 알림, 실 상담원 PC 검증, 데이터 보존 정책을 우선한다.

## 2. 범위

### P3-1 운영 배포/릴리즈 안정화

목표: 운영 site 단위로 배포, migration, rollback, smoke gate를 반복 가능한 절차로 만든다.

작업:

- 운영 site별 `.env`, DB URL, Redis, PBX 접속값, CORS, WebSocket URL을 확정한다.
- `scripts/deploy-prod.sh`와 `deploy/sites/_template` 기준으로 staging/production 배포 preflight를 정리한다.
- migration 적용 전/후 확인 절차와 실패 시 중단 기준을 문서화한다.
- `/etc/asterisk` 공유 마운트 owner guard를 운영 배포 절차에 포함한다.
- 배포 후 `health`, Swagger, 관리자 앱, 상담원 앱, PBX smoke gate를 순서대로 실행한다.
- rollback 기준과 이전 이미지/설정 복구 절차를 문서화한다.

완료 기준:

- 운영 site 값만 넣으면 같은 순서로 배포와 검증을 반복할 수 있다.
- PBX 설정 owner 충돌, migration 실패, health 실패, smoke 실패가 배포 중단 조건으로 명확히 남는다.

### P3-2 외부 알림 채널 연동

목표: P2 운영 모니터링 지표를 관리자 화면 밖으로도 전달한다.

작업:

- 1차 알림 채널을 확정한다. 후보는 Slack, 이메일, SMS다.
- 알림 sink 인터페이스를 정의하고 credential 주입 방식을 정한다.
- PBX AMI disconnect, Redis 장애, DB 장애, outbox backlog, RECOVERY_TIMEOUT 급증의 발생/복구 알림을 정의한다.
- 같은 장애가 반복될 때 중복 알림을 억제하는 기준을 정한다.
- 관리자 화면의 알림 배열과 외부 알림의 기준이 어긋나지 않게 한다.

완료 기준:

- 운영자가 관리자 화면을 보고 있지 않아도 장애 발생과 복구를 받을 수 있다.
- 중복 알림과 복구 알림 기준이 문서와 코드에 같이 반영된다.

### P3-3 실 상담원 PC 현장 검증

목표: 실제 Windows 상담원 PC와 현장 네트워크에서 상담원 업무 흐름을 통과시킨다.

작업:

- `docs/qa/desktop-live-test-template.md`를 현장 테스트 기록지로 사용한다.
- pairing, SIP 등록, 수신, 발신, 종료를 검증한다.
- 마이크, 스피커, 벨소리 장치 선택과 재시작 후 유지 여부를 확인한다.
- 웹 앱과 데스크톱 앱의 통화 상태가 같은지 확인한다.
- 통화 중 앱 재시작, 네트워크 단절, CTI 서버 재시작 복구 시나리오를 확인한다.

완료 기준:

- 실제 상담원 PC에서 기본 상담 업무 흐름이 통과한다.
- 실패가 있으면 PC/네트워크/서버/앱 중 어느 구간인지 증적으로 분리된다.

### P3-4 운영 데이터 보존/정리 정책

목표: 운영 감사와 장애 분석에 필요한 데이터는 보존하고, 불필요한 데이터는 정리한다.

작업:

- 녹취 다운로드 감사 로그 온라인 보관 기간을 확정한다. P2 기준은 1년이다.
- raw AMI event, event outbox, smoke report, 서버 로그의 보관 기간을 정한다.
- 오래된 테스트 데이터와 운영 데이터의 정리 기준을 분리한다.
- 정리 작업을 수동 절차로 둘지 scheduled job으로 둘지 결정한다.

완료 기준:

- 감사/장애 분석에 필요한 데이터가 임의로 삭제되지 않는다.
- 운영 DB와 파일 저장소가 무기한 증가하지 않도록 정리 기준이 있다.

## 3. P3에서 제외하는 항목

- P2에서 이미 완료된 관리자 리포트의 추가 UI 확장은 운영 피드백이 들어온 뒤 별도 phase로 다룬다.
- 새로운 CRM/외부 시스템 연동은 운영 배포와 현장 검증이 안정화된 뒤 별도 범위로 분리한다.
- 실제 운영 PBX 값이 확정되지 않은 상태에서 production 설정을 추정해 커밋하지 않는다.

## 4. 필요 입력값

P3 착수 전에 다음 값이 필요하다.

- 운영 site 이름과 서버 접속 기준
- 운영 DB/Redis/PBX/AMI endpoint와 credential 주입 방식
- 운영 관리자/상담원 앱 public URL
- 외부 알림 채널과 credential
- 실 상담원 PC 접근 가능 시간, 내선, 헤드셋/오디오 장치 정보
- 운영 rollback 허용 기준과 담당자

## 5. 실행 순서

1. P3-1 운영 배포/릴리즈 안정화 착수
2. P3-2 외부 알림 채널 결정 및 notification contract 작성
3. P3-3 실 상담원 PC 현장 검증 수행
4. P3-4 운영 데이터 보존/정리 정책 확정

## 6. 첫 작업

첫 작업은 P3-1 운영 배포/릴리즈 안정화다.

구체적으로는 현재 `deploy/sites/_template`, `scripts/deploy-prod.sh`, PBX 설정 owner guard, smoke gate를 기준으로 운영 site preflight 문서를 만들고, 실제 site 값이 들어왔을 때 바로 실행 가능한 순서로 정리한다.

# Agent Desktop Architecture Design

- Date: 2026-04-22
- Status: Proposed
- Scope: 상담원 단말의 WebRTC 도입 방향, 웹과 데스크톱의 책임 분리, 외부 CRM 연동 API 규칙 초안

## Background

현재 상담원 제품은 `apps/web` 중심의 브라우저 SPA 구조다. 이 앱은 상태 관리, 현재 콜 표시, 발신/전환/종료 요청, 실시간 이벤트 수신까지는 이미 담당하고 있다. 반면 실제 미디어 세션, 오디오 장치 제어, 헤드셋 운영, 브라우저 권한과 포커스 문제는 아직 구조적으로 다루지 않고 있다.

운영 전제는 다음과 같다.

- 상담원 단말은 사내 관리형 Windows PC다.
- 앱 설치, 자동 업데이트, 시작 프로그램 등록, 백그라운드 프로세스 실행이 가능하다.
- 장기적으로는 자체 CRM 기능까지 제품에 포함할 계획이다.
- 외부 CRM은 핵심 제품이 아니라 요청 시 연동해 주는 확장 포인트로 본다.

이 전제에서는 브라우저 웹 단독으로 통화 기능까지 확장하는 것보다, 통화와 장치 제어를 별도 실행체로 분리하는 방향이 더 적합하다.

## Problem Statement

WebRTC 기반 소프트폰을 기존 웹 앱 안에 직접 넣는 방식은 초기 구현은 빠를 수 있지만 다음 리스크가 있다.

- 브라우저 권한, 탭 생명주기, 새로고침, 포커스 이동, 다중 탭 사용이 통화 안정성에 직접 영향을 준다.
- 헤드셋, 마이크, 스피커, 벨소리, 오디오 라우팅, 장치 장애 복구가 브라우저 UX와 강결합된다.
- 외부 CRM 연동 시 동일 브라우저 안에서 팝업, 포커스, 스크린팝, 인증 컨텍스트 전달이 복잡해진다.
- 향후 자체 CRM까지 웹 단일 앱에 계속 적층하면 업무 UI와 통화 런타임이 하나의 거대한 SPA로 결합된다.

반대로 Windows 데스크톱 앱은 설치와 업데이트 비용이 있지만, 통화 단말에 필요한 운영 제어권과 사용자 경험 일관성을 확보할 수 있다.

## Goals

- 상담원 통화 경험의 안정성을 브라우저 제약과 분리한다.
- 현재 웹 기반 업무 UI를 유지하면서도 향후 자체 CRM으로 확장 가능한 구조를 만든다.
- 외부 CRM 연동에 재사용 가능한 표준 API 규칙을 정의한다.
- 단계적으로 도입 가능한 구조를 선택해 초기 투자와 장기 유지보수의 균형을 맞춘다.

## Non-Goals

- 이번 단계에서 데스크톱 앱의 기술 스택이나 특정 프레임워크를 확정하지 않는다.
- 이번 단계에서 외부 CRM별 커넥터 구현 방식을 상세 설계하지 않는다.
- 이번 단계에서 관리자 대시보드나 supervisor 전용 화면을 데스크톱 앱으로 이관하지 않는다.

## Options Considered

### Option A: Existing Web App + WebRTC Expansion

기존 `apps/web`에 WebRTC와 소프트폰 제어를 직접 추가한다.

장점:

- 기존 UI와 인증 흐름을 최대한 재사용할 수 있다.
- 초기 PoC 속도가 가장 빠르다.
- 배포 대상이 웹 하나라서 설치 부담이 없다.

단점:

- 브라우저가 업무 셸과 통화 엔진을 동시에 맡아 책임이 과도하게 커진다.
- 오디오 장치 제어와 브라우저 생명주기 이슈를 안정적으로 다루기 어렵다.
- 외부 CRM과 함께 열려 있을 때 포커스와 알림 일관성이 약하다.
- 장기적으로 자체 CRM까지 확장하면 복잡도가 급격히 상승한다.

평가:

PoC나 단기 검증에는 가능하지만, 본 프로젝트의 장기 방향으로는 부적합하다.

### Option B: Hybrid Model with Web CRM and Desktop Call Runtime

업무 UI와 CRM은 웹이 담당하고, 통화 엔진과 장치 제어는 별도 Windows 앱이 담당한다.

장점:

- 현재 웹 자산을 유지하면서 통화 안정성을 별도 런타임으로 확보할 수 있다.
- 오디오 장치, 백그라운드 대기, 시작 시 자동 실행, 알림, 포커스 제어를 안정적으로 다룰 수 있다.
- 향후 자체 CRM이 커져도 웹과 통화 엔진을 독립적으로 확장할 수 있다.
- 외부 CRM 연동이 필요할 때에도 CTI 플랫폼과 업무 화면을 느슨하게 결합할 수 있다.

단점:

- 클라이언트 배포와 자동 업데이트 체계가 필요하다.
- 웹과 데스크톱 간 세션 동기화, 상태 동기화 정책을 설계해야 한다.
- 운영팀이 단말 배포와 버전 관리 책임을 져야 한다.

평가:

현재 운영 전제와 장기 제품 방향을 동시에 만족하는 가장 균형 잡힌 선택지다.

### Option C: Full Desktop Agent Client

상담 업무 UI와 CRM, 소프트폰, 알림, 설정을 모두 전용 데스크톱 앱에 통합한다.

장점:

- 사용자 경험과 장치 제어를 강하게 통제할 수 있다.
- 장기적으로 가장 일관된 상담원 제품이 될 수 있다.

단점:

- 지금 시점에서 범위가 너무 크고 제품 전략을 조기에 고정한다.
- CRM 요구사항이 계속 바뀌는 시기에 데스크톱 UI까지 같이 고정하면 변경 비용이 커진다.
- 배포, QA, 회귀 테스트 범위가 크게 증가한다.

평가:

최종 상태로는 가능하지만 지금 바로 선택할 초기 전략은 아니다.

## Recommendation

권장안은 Option B다.

즉, `웹은 업무 셸`, `데스크톱은 통화 런타임`, `서버는 상태 기준 시스템`으로 역할을 분리한다. 이 구조는 현재 웹 자산을 살리면서도 통화 안정성과 장치 제어 문제를 브라우저 밖으로 분리한다. 또한 장기적으로 자체 CRM이 커지면 웹 CRM을 계속 확장하거나, 이후 데스크톱 셸 안으로 수용하는 경로를 모두 열어 둔다.

이 권장안은 최종 제품을 “상담원 전용 클라이언트” 방향으로 진화시키되, 지금 당장은 가장 리스크가 큰 미디어/장치 책임만 데스크톱으로 먼저 옮기는 전략이다.

## Target Architecture

### Core Principle

- 웹은 고객 정보, 상담 흐름, 메모, 이력, 상태 관리, 향후 CRM 화면을 담당한다.
- 데스크톱 앱은 WebRTC 또는 SIP 미디어 세션, 장치 제어, 착신 팝업, 통화 제어 UX를 담당한다.
- NestJS 서버는 인증, 상담원 세션, 호 상태, 통화 제어 명령, 이벤트 방송의 기준 시스템으로 남는다.

### Logical Components

1. Web Agent Shell

- 기존 `apps/web` 기반
- 로그인, 상태 변경, 고객/통화 정보 표시, 메모 저장, 전환 요청 등 업무 중심 기능 담당
- 장기적으로 자체 CRM 기능이 이 레이어에서 성장

2. Desktop Call Runtime

- Windows 상주형 상담원 단말
- 로그인 세션 연계
- 착신 알림, 통화 수락/종료, 음소거, 보류, 전환
- 마이크/스피커/헤드셋 선택 및 장애 감지
- 네트워크 이상, 재등록, 재연결 상태 표시

3. CTI Middleware Server

- 현재 `apps/server`
- 인증, call session, AMI 이벤트 정규화, WebSocket 이벤트 전파, 호제어 API 유지
- 데스크톱과 웹 모두 동일한 서버 상태를 기준으로 동작

4. Optional Local Bridge

- 필요할 경우 웹과 데스크톱 사이에 로컬 IPC 또는 loopback bridge를 둔다.
- 초기 설계에서는 필수 구성요소가 아니다.
- 우선은 서버 중심 동기화로 설계하고, 로컬 직접 제어가 필요한 경우에만 도입한다.

### High-Level Data Flow

1. 상담원 로그인

- 웹 또는 데스크톱 중 하나가 로그인한다.
- 서버는 상담원 세션과 토큰을 발급한다.
- 다른 클라이언트는 위임 세션 또는 짧은 수명의 handoff 토큰으로 세션을 연계한다.

2. 인바운드 콜 수신

- 서버가 AMI 이벤트를 조립해 세션 상태를 갱신한다.
- 웹은 고객 정보와 업무 패널을 갱신한다.
- 데스크톱은 착신 알림과 소프트폰 제어 UI를 띄운다.

3. 통화 제어

- 사용자가 데스크톱에서 수락, 종료, 전환, 음소거를 수행한다.
- 데스크톱은 서버의 명령 API를 호출한다.
- 실제 성공 여부는 후속 이벤트를 서버가 조립해 웹과 데스크톱에 동시에 전파한다.

4. 통화 후 작업

- 웹은 ACW, 메모, 결과 코드, CRM 후처리를 담당한다.
- 데스크톱은 필요한 경우 통화 종료 후 최소 컨텍스트만 유지하고 주 책임은 웹으로 넘긴다.

## Desktop App Responsibility Boundary

### Must-Have Responsibilities

- 로그인 세션 연계
- 인바운드 착신 알림
- 통화 수락/종료
- 음소거
- 보류/재개
- Blind/Attended transfer UX
- 오디오 장치 선택과 상태 표시
- 헤드셋 연결 상태 감지
- 네트워크/세션 이상 감지
- 백그라운드 대기 및 재실행 후 복구

### Should-Not-Own Responsibilities in Phase 1

- 고객 상세 편집
- 상담 이력 검색 UI
- 복잡한 CRM 화면
- 관리자/감독자 기능
- 마스터 데이터 관리
- 보고서/대시보드

이 범위 제한이 중요하다. 1차 데스크톱 앱을 “작은 소프트폰 + 운영 가능한 통화 런타임”으로 유지해야, 빠르게 안정화하고 추후 자체 CRM 확장 여부를 다시 판단할 수 있다.

## API Contract Rules for External CRM

외부 CRM 연동은 특정 CRM 제품에 맞춘 임시 스크립트가 아니라, CTI 플랫폼이 제공하는 표준 계약으로 설계해야 한다. 이 계약은 나중에 자체 CRM에도 그대로 재사용할 수 있어야 한다.

### Contract Families

1. Query APIs

- 현재 상담원 세션 조회
- 현재 활성 콜 조회
- 고객 식별 결과 조회
- 큐 상태 및 배정 상태 조회
- 콜 컨텍스트 조회

2. Command APIs

- 발신 요청
- 수신/당겨받기 요청
- 종료 요청
- 전환 요청
- 보류/재개
- 상담원 상태 변경
- 통화 후 결과 저장

3. Event Streams

- 착신 발생
- 상담원 벨 울림
- 통화 연결
- 통화 종료
- 전환 단계 변경
- 상담원 상태 변경
- 스크린팝 요청

### Required Field Rules

모든 주요 계약에는 아래 식별자 규칙을 일관되게 사용한다.

- `tenantId`
- `agentId`
- `callId`
- `linkedid`
- `occurredAt`
- `correlationId`

명령 API에는 `idempotencyKey`를 받는다. 사용자는 더블 클릭, 네트워크 재시도, 클라이언트 재전송을 할 수 있으므로, CTI 명령은 기본적으로 멱등 설계를 따른다.

### Result Semantics

명령 API는 즉시 성공 확정을 반환하지 않는다.

- 동기 응답: `accepted`, `requestedAt`, `correlationId`
- 최종 결과: 후속 이벤트에서 판단

이 규칙은 현재 서버의 호제어 모델과도 일치한다. 외부 CRM이 REST 응답만 보고 통화 성패를 단정하지 않도록 막아 준다.

### Screen Pop Contract

외부 CRM 및 자체 CRM 모두 아래 인터페이스를 기준으로 설계한다.

- 착신 시 고객 식별 요청
- 콜별 CRM 레코드 조회 또는 생성
- 통화 종료 후 결과 코드 저장
- 상담 메모 업로드
- CRM 객체 링크 반환

이 계약을 표준화하면 외부 CRM은 얕은 링크 연동부터 깊은 양방향 연동까지 단계적으로 붙을 수 있다.

## Authentication and Session Strategy

브라우저 `localStorage` 기반 순수 SPA 토큰 구조는 현재 웹에는 충분하지만, 웹과 데스크톱이 공존하는 단계에서는 세션 위임 규칙이 추가로 필요하다.

권장 원칙은 다음과 같다.

- 상담원 본인 인증은 서버가 직접 수행한다.
- 웹과 데스크톱은 동일 refresh token을 공유하지 않는다.
- 1차 로그인 후 다른 클라이언트로 세션을 연결할 때는 짧은 수명의 handoff token 또는 device-bound delegated token을 사용한다.
- 각 클라이언트 세션은 서버에서 독립적으로 revoke 가능해야 한다.
- 장기 토큰을 임의 외부 CRM 프런트엔드 JavaScript에 직접 노출하지 않는다.

## Error Handling and Failure Modes

### Desktop App Failure

- 앱 재시작 시 서버 기준 현재 상담원 세션과 활성 콜을 재동기화한다.
- 미디어 세션이 끊겨도 서버 기준 상태를 먼저 조회해 UI를 복원한다.
- 장치 접근 실패 시 명확한 에러 상태와 복구 경로를 보여 준다.

### Web App Failure

- 웹이 새로고침되더라도 서버 기준 현재 콜과 상담 상태를 다시 조회해 복구한다.
- 통화는 데스크톱이 계속 유지하므로 업무 UI 재기동이 통화 종료를 유발하지 않아야 한다.

### Server or Transport Failure

- 웹과 데스크톱 모두 websocket 단절을 감지하고 재연결한다.
- 재연결 후에는 이벤트 재수신만 믿지 말고 현재 상태 조회 API로 정합성을 복원한다.
- 명령 API 재시도 시에는 `idempotencyKey`를 사용한다.

## Delivery Phases

### Phase 1: Architecture Hardening

- 웹과 통화 런타임의 책임 경계를 문서화
- 서버 API 계약에 `correlationId`, `idempotencyKey`, 이벤트 의미 규칙 추가
- 웹을 “업무 셸” 관점으로 정리

### Phase 2: Minimal Desktop Call Runtime

- 로그인 세션 연계
- 착신 알림
- 통화 수락/종료
- 음소거, 보류, 전환
- 장치 선택

### Phase 3: Web and Desktop Coexistence

- 웹과 데스크톱 동시 로그인 정책
- CRM 화면과 통화 팝업 간 컨텍스트 이동 정책
- 장애 복구, 재연결, 상태 재동기화 검증

### Phase 4: External CRM Contract Formalization

- 외부 CRM용 인증 모델
- 표준 조회/명령/이벤트 계약 문서화
- 스크린팝과 후처리 인터페이스 정의

### Phase 5: Evaluate Full Agent Desktop

- 자체 CRM이 충분히 성숙하면 웹 CRM을 계속 유지할지, 데스크톱 셸로 흡수할지 결정
- 이 판단은 실제 운영 데이터와 사용자 피드백을 기준으로 한다.

## Testing Strategy

이번 문서는 구현이 아니라 방향 설계이므로 테스트는 설계 검증 관점에서 정의한다.

- 상담원 업무 웹이 내려가도 통화가 유지되는지 검증
- 데스크톱 앱 재시작 후 현재 통화와 상태가 복원되는지 검증
- 네트워크 단절 후 재연결 시 상태가 서버 기준으로 수렴하는지 검증
- 외부 CRM이 이벤트 지연 또는 중복을 받아도 멱등하게 처리 가능한지 검증
- 전환, 종료, 보류 등의 명령이 중복 제출돼도 서버가 안전하게 처리하는지 검증

## Open Decisions Deferred

아래 항목은 다음 계획 단계에서 결정한다.

- 데스크톱 앱 기술 스택
- WebRTC 종단 구조와 SIP 연동 상세
- 데스크톱 배포/업데이트 도구 선택
- 웹과 데스크톱 간 직접 IPC 필요 여부
- 외부 CRM 인증 방식의 구체 프로토콜

## Final Decision

현재 프로젝트는 `웹 단독 WebRTC 확장`이 아니라 `웹 CRM + Windows 통화 런타임` 하이브리드 구조를 기준으로 진행한다.

이 구조는 현재 운영 환경에 맞고, 통화 안정성과 장치 제어에 유리하며, 향후 자체 CRM 제품으로 확장할 때도 구조적 재작업을 최소화한다.

# 핫링크 vs SIP 표준 — Hybrid 아키텍처 제안

> 원본: ChatGPT 대화 `69ddf38c-9ed4-83ab-a98e-61b34a363d7e` — "콜센터 통화 최적화 방법"  
> `docs/chatgpt-archive/conversations.json` 에서 추출.

대리운전 업계에서 흔히 쓰는 **핫링크 (상담원 사전 연결 + 별도 제어 프로토콜 + 서버 음성 릴레이)** 방식의 장단점과, 이에 대한 **Hybrid (제어는 앱/Middleware, 음성은 PBX 브리지)** 대안을 정리합니다. "왜 완전 핫링크를 쓰지 않는가?"라는 재질문에 대한 근거 문서입니다.

---

## 💬 질문 1

대리운전 콜센터는 대부분 핫링크 방식을 사용한다.
상담원 로그인시 미리 연결을 해둔 상태에서 상담원과 고객의 통화를 연결해 줄때는 sip 프로토콜을 통하지 않고 별도의 제어용 프로토콜을 설계해서 사용한다.
상담원 호 분배 규칙에 의해 해당 상담원에게 호 전달해서 상담원이 수락시에 서버가 음성 릴레이를 통해 통화를 연결해준다. 만일 상담원들이 호 당겨받기를 사용해서 통화를 원할경우 상담원 앱을 통해 당겨받기 커맨드를 이용해서 고객의 호를 획득하여 연결된 경우에 음성 중계를 통해 통화를 한다.
이를 사용하는 이유는 상담원과 고객의 통화 연결시 invite -> accept -> ack 등의 과정을 거치는 동안 고객의 대기 시간이 발생하는 것을 예방하기 위한 것이다.
이 방법의 단점은 네트웍 부하, 별도의 제어 프로토콜의 개발, 음성 중계에 의한 부하 등이 있을수 있다. 
더 좋은 방법이 있다면 제안해줘. 

## 🤖 답변 6

현재 방식의 장단점을 기준으로, 더 나은 대안을 아키텍처 관점에서 정리해보겠습니다. 지금 구조는 “상담원 대기시간 최소화”에는 강하지만, 음성 경로와 제어 경로를 따로 만드는 비용이 꽤 큽니다.

## 🤖 답변 7

핫링크 방식이 현장에서 많이 쓰이는 이유는 분명합니다.  
말씀하신 것처럼 고객 호를 먼저 서버 쪽에 붙잡아 두고, 상담원은 이미 로그인 시점에 미리 연결된 세션을 유지한 뒤, 실제 연결 순간에는 별도 제어 프로토콜로 “누가 받을지”만 결정하면 되기 때문에 SIP의 `INVITE -> 180/183 -> 200 OK -> ACK` 구간에서 생기는 체감 지연을 줄이기 좋습니다.

다만 이 구조는 결국 **제어 최적화 대신 미디어 비용을 더 내는 구조**입니다.  
즉, 상담원 응답 지연은 줄지만, 그 대가로:

- 서버가 항상 음성 릴레이 구간에 들어감
- 제어 프로토콜을 별도로 개발/운영해야 함
- 상담원 수가 늘수록 미디어 처리 부하와 장애 포인트가 커짐
- SIP 표준 생태계 기능을 충분히 활용하기 어려움

이 단점이 있습니다.

업로드된 현재 설계 문서도 기본 원칙은 **Asterisk는 통화 제어에 집중하고, CTI Middleware는 이벤트 정규화와 업무 로직을 담당**하는 구조를 권장하고 있습니다. 즉, PBX는 PBX답게 쓰고, 업무 로직은 미들웨어에서 처리하는 분리형 구조가 기본 방향입니다. fileciteturn0file1L10-L19 또한 인바운드 기본 흐름도 `SIP Trunk -> Asterisk -> IVR/Queue -> 상담원 분배 -> Middleware 이벤트 처리`를 중심으로 설명하고 있어, 음성 경로를 별도 릴레이 시스템으로 완전히 우회하는 형태보다는 PBX 중심 구조에 가깝습니다. fileciteturn0file1L55-L71

제가 보기에는 “더 좋은 방법”은 핫링크를 완전히 버리는 것보다는, 아래 3가지 방식 중에서 선택하는 것입니다.

## 1. 가장 권장: **SIP 표준 유지 + 상담원 단말 사전등록 + Queue 최적화**
이 방식은 핫링크의 장점을 일부 가져오되, 미디어 릴레이를 불필요하게 늘리지 않는 방법입니다.

핵심은:

- 상담원 앱/소프트폰은 항상 SIP 등록 상태 유지
- 고객 호는 Asterisk Queue에서 대기
- 상담원 분배는 `app_queue` 또는 ARI/AMI 기반으로 수행
- 상담원 벨 울림 시간은 최소화
- 고객에게는 early media, 안내음, 대기 멘트 제공
- 상담원 수락 즉시 브리지

이미 설계서에서도 Queue 정책 권고로 `leastrecent/fewestcalls`, `timeout 15~20초`, `retry 2~3초`, `wrapuptime`, `autopause` 등을 제안하고 있습니다. fileciteturn0file1L132-L141  
또한 산출물 문서에서도 `queues.conf` 기준으로 `strategy=leastrecent`, `timeout=15`, `retry=3`, `autopause=yes`, `ringinuse=no` 형태를 기본값으로 잡고 있습니다. fileciteturn0file2L614-L629

이 방식의 장점은:

- 별도 음성 릴레이 시스템이 없어도 됨
- SIP 표준을 유지하므로 확장성이 좋음
- 녹취, 전환, 보류, Queue 통계가 Asterisk 기본 모델과 잘 맞음
- 디버깅이 쉬움

단점은:

- 상담원 수락까지 아주 짧은 체감 지연은 남음
- 모바일망, 불안정한 softphone 환경에서는 ringing/answer 편차가 생김

즉, **대부분의 일반 콜센터에는 이 방식이 총비용 대비 가장 낫습니다.**

---

## 2. 현실적 타협안: **제어는 앱, 미디어는 PBX 표준 브리지**
이건 현재 생각하신 핫링크 구조를 더 안전하게 바꾸는 방식입니다.

구조는 이렇게 갑니다.

- 상담원 앱은 서버와 WebSocket 또는 전용 제어 채널로 연결
- 앱은 “대기 가능”, “수락”, “당겨받기”, “후처리” 같은 제어만 담당
- 실제 음성 연결은 별도 음성 릴레이 서버가 아니라 **Asterisk가 브리지**
- 상담원이 수락하면 서버가 AMI/ARI로 Asterisk에 브리지 명령
- 상담원 음성 경로도 가능하면 SIP endpoint 또는 WebRTC endpoint로 직접 연결

즉,  
**별도 제어 프로토콜은 유지하되, 음성 중계 전용 서버는 없애거나 최소화**하는 방식입니다.

현재 문서에서도 AMI는 이벤트 수집 중심, ARI는 특수 콜 제어에 단계적으로 적용하는 것을 권고합니다. fileciteturn0file1L17-L19  
또 산출물 문서 역시 콜 제어 요청은 미들웨어가 권한 확인과 세션 정합성 검사를 거쳐 **AMI/ARI 또는 내부 서비스로 위임**하도록 정의합니다. fileciteturn0file2L466-L473

이 방식의 장점은:

- 기존 핫링크 UX를 어느 정도 유지 가능
- 상담원 앱 중심의 당겨받기/수락 UX 구현 가능
- 미디어 경로를 PBX 표준 기능에 맡겨 운영 복잡도가 줄어듦
- 별도 RTP 릴레이 서버 병목이 줄어듦

단점은:

- 앱-서버-ARI/AMI-Asterisk 연동 설계가 필요
- SIP 단말 또는 WebRTC 단말 구조를 정교하게 잡아야 함

저는 **대리운전 콜센터처럼 당겨받기와 빠른 선점 UX가 중요한 경우 이 방식을 가장 추천**합니다.

## 3. 특수 목적에만 권장: **완전 핫링크 + 서버 음성 릴레이**
이건 지금 말씀하신 방식 그대로입니다.

적합한 경우는:

- 상담원 앱이 SIP 단말이 아니라 완전 커스텀 음성 앱일 때
- 수락/선점 UX가 SIP 표준보다 훨씬 중요할 때
- 수백 석 이하의 제한된 규모에서 빠른 응답성을 최우선할 때
- 서버 증설과 미디어 분산 구조를 감당할 수 있을 때

하지만 이 방식은 규모가 커질수록:

- RTP relay 처리량
- NAT 처리
- codec transcoding 가능성
- 녹취/전환/보류 정합성
- 장애 시 전체 통화 영향

문제가 커집니다.

즉, **기술적으로 가능하지만 장기적으로는 운영비가 비쌉니다.**

## 더 나은 방향으로 구체 제안

제안 순위는 이렇습니다.

### A안. 가장 균형 좋음
**Asterisk Queue + SIP/WebRTC 상담원 단말 + 앱 제어 보조**

- 상담원은 SIP 또는 WebRTC로 항상 등록
- 고객 호는 Queue 대기
- 앱은 고객정보 팝업, 수락, 후처리, 당겨받기 요청만 담당
- 실제 브리지는 Asterisk가 수행
- 당겨받기는 앱에서 요청 → Middleware → ARI/AMI → 해당 상담원 채널에 연결

이 구조는 지금 문서의 “Asterisk는 통화 제어, Middleware는 정규화/업무 처리” 원칙과 가장 잘 맞습니다. fileciteturn0file1L10-L19 fileciteturn0file2L27-L35

### B안. 대리운전 업종 최적화형
**Pre-call leg 준비 + 실제 connect만 PBX 브리지**

- 상담원 앱은 로그인 시 signalling/session 준비
- 하지만 음성은 항상 서버가 릴레이하지 않음
- 고객이 배정되면 상담원에게 매우 짧은 pre-alert
- 수락 즉시 PBX가 브리지
- 수락 전 고객에게는 ringback/안내음 제공

이 방식은 체감 대기시간은 거의 유지하면서, 미디어 비용은 크게 줄일 수 있습니다.

### C안. 대규모 운영형
**초기 핫링크 → 점진적으로 SIP/WebRTC 하이브리드 전환**

- 기존 운영 로직 유지
- 신규 상담원 앱은 WebRTC/SIP 기반으로 개발
- 기존 핫링크는 일부 조직만 유지
- Queue, 녹취, 모니터링, 통계는 전부 Asterisk 기준으로 통합

이렇게 가면 기존 업무를 깨지 않고 이전할 수 있습니다.

## 특히 대리운전 콜센터라면 고려해야 할 점

대리운전은 일반 고객센터와 달리:

- 응답 속도가 매우 중요하고
- 상담원 당겨받기 문화가 강하고
- 짧은 콜이 많고
- 동시성 피크가 급격히 올라갈 수 있습니다

그래서 완전 정석 SIP만으로 가면 현업이 답답하다고 느낄 수 있습니다.  
반대로 완전 핫링크는 운영비가 커집니다.

그래서 가장 현실적인 답은:

**“제어는 앱 중심, 음성은 PBX 브리지 중심”** 입니다.

즉,

- 당겨받기, 우선 수락, 선점 로직, 상태 관리 = 앱/미들웨어
- 실제 음성 연결, 녹취, 전환, 통계 = Asterisk

로 역할을 나누는 게 좋습니다.

## 결론

지금 방식은 “빠른 연결”이라는 목적에는 맞지만, 장기 운영 기준으로는 **미디어 릴레이 비용과 자체 제어 프로토콜 유지보수 비용이 너무 큽니다.**

더 좋은 방법은 완전 대체보다 **하이브리드화**입니다.

가장 추천하는 구조는:

**1) 상담원 제어는 앱에서 한다**  
**2) 호 분배 판단은 Middleware가 한다**  
**3) 실제 음성 연결은 Asterisk가 브리지한다**  
**4) ARI/AMI로 당겨받기·수락·전환만 정교하게 제어한다**

이렇게 하면:

- 고객 대기 체감시간은 짧게 유지
- 별도 음성 릴레이 부하는 감소
- 녹취/통계/운영도 쉬워짐
- SIP 표준 생태계를 최대한 활용 가능

합니다.

원하시면 다음 단계로 바로 이어서  
**“대리운전 콜센터용 하이브리드 핫링크 아키텍처”**를 기준으로

- Asterisk/ARI 기반 콜 플로우
- 상담원 앱 제어 프로토콜 초안
- 당겨받기 상태머신
- 서버 구성도
- 장단점 비교표

까지 실전 설계 형태로 정리해드리겠습니다.

## 핵심 정리 (요약)

### 1. 기존 방식 (핫링크)
- 상담원 미리 연결 + 별도 제어 프로토콜
- 음성은 서버 릴레이 방식

👉 장점  
- 빠른 연결 (대기시간 최소화)  
- 당겨받기 UX 우수  

👉 단점  
- 서버 부하 큼 (RTP 릴레이)  
- 자체 프로토콜 유지 비용  
- 확장성/안정성 문제  

---

### 2. 제안 방식 (Hybrid 구조)

👉 핵심 컨셉  
**“제어는 앱 + 음성은 PBX(Asterisk)”**

구조:
- 상담원 제어 → 앱 + Middleware
- 콜 분배 → Middleware
- 실제 통화 연결 → Asterisk 브리지

---

### 3. 콜 흐름

1. 고객 인입 → Queue 대기  
2. Middleware가 상담원 선택  
3. 상담원 앱에 이벤트 전달  
4. 상담원 수락 / 당겨받기  
5. Asterisk가 즉시 브리지 연결  

---

### 4. 효과

- 음성 서버 부하 감소
- SIP 표준 유지 (확장성 ↑)
- 기존 UX 유지 (빠른 응답)
- 운영/장애 대응 쉬움

---

### 5. 결론

👉 완전 핫링크 ❌  
👉 완전 SIP만 ❌  

👉 **Hybrid (제어 분리 + PBX 브리지) = 최적**

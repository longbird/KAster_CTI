# PBX 선별 수용 기능별 개발 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 기존 디지털 키폰 PBX 기능 중 현재 CTI 운영에 필요한 기능만 선별해 관리자 설정, CTI 백엔드, PBX 설정 반영 구조에 단계적으로 통합한다.

**Architecture:** 기존 `지사 관리`, `PBX 설정`, `호 분배룰 설정`, `상담원 설정`, `시스템 설정` 화면을 우선 확장하고, 저장/검증/API 계층과 PBX 설정 렌더링 계층을 분리한다. 번호 자원은 운영 정책과 충돌 검증, 기능 코드는 별도 PBX 명령/단축 접근 체계로 다룬다.

**Tech Stack:** NestJS, Prisma, PostgreSQL, Redis, React, Vite, Ant Design, PBX 설정 렌더러, Jest/Vitest 계열 테스트.

## 구현 원칙

- PBX 문서/화면 용어는 `PBX`로 통일한다. 내부 파일 경로와 기존 코드 식별자는 당장 변경하지 않는다.
- 기존 디지털 키폰 PBX는 참고 자료일 뿐 기준점이 아니다. CTI 운영에 필요한 기능만 수용한다.
- 실시간 통화 감청은 개발 범위에서 제외한다.
- 번호 자원과 기능 코드는 별도 영역으로 유지한다.
- 번호 자원은 기능 구현 기반이 아니라 운영 정책, 충돌 검증, 관리자 화면 이동 보조 정보로 다룬다.
- 새 관리자 메뉴를 추가할 경우 서버 메뉴 권한과 프론트 메뉴 설정을 동시에 갱신한다.
- Prisma 스키마를 변경하는 작업은 마이그레이션 작성 후 `npx prisma generate`를 반드시 실행한다.
- PBX 설정 파일로 반영되는 기능은 저장 API와 PBX 렌더러 테스트를 분리해서 검증한다.
- 각 기능별 설정 페이지에는 도움말 아이콘을 배치하고, 접근 또는 클릭 시 해당 기능의 설명, 설정 방법, 주의사항, 적용 예시를 즉시 확인할 수 있어야 한다.
- 도움말 내용은 수동으로 고정 문구만 작성하지 않고, 참조 매뉴얼과 정보 검색 결과를 기반으로 자동 구축하되 최종 화면에는 출처와 검토 상태를 함께 표시한다.

### 부분 완료 또는 남은 확인

- 국선 표시번호: 허용/기본 발신번호, 지사 발신번호 권한, outbound caller ID PBX 렌더링과 별개로 트렁크 단위 `displayNumber` 모델, PBX 트렁크 목록 `표시번호` 열, 트렁크 저장/조회 테스트를 추가했다.
- 시간 동기화: 앱/DB 시간 차이 조회에서 AMI `Command` 기반 PBX 시간 조회로 보강했다. PBX 시간 명령이 실패하거나 파싱되지 않으면 `UNKNOWN`으로 내려 운영자가 확인할 수 있다.

## 공통 도움말 기능 개발 계획

**판단:** 즉시 개발. PBX 기능은 운영자가 용어와 설정 효과를 혼동하기 쉬우므로, 각 기능별 설정 화면에서 바로 확인 가능한 도움말이 필요하다. 도움말은 기능 구현과 함께 유지되어야 하며, 매뉴얼 기반 설명과 실제 운영 정책을 함께 반영해야 한다.

### 사용자 경험

- [ ] 각 기능별 페이지, 모달, 주요 설정 섹션 제목 오른쪽에 도움말 아이콘을 표시한다.
- [ ] 아이콘은 키보드 포커스 접근이 가능해야 하며 `aria-label`에는 `도움말 보기: 기능명` 형식을 사용한다.

- [ ] 상세 도움말에는 `기능 설명`, `설정 방법`, `운영 예시`, `주의사항`, `관련 설정`, `출처`, `마지막 갱신일`, `검토 상태`를 포함한다.
- [ ] 도움말에서 관련 설정으로 이동할 수 있는 내부 링크를 제공하되, 사용자가 작성 중인 설정값을 잃지 않도록 현재 모달/페이지 상태를 보존한다.

- [x] 대리응답이 `울리고 있는 특정 내선의 전화를 다른 상담원이 당겨 받는 기능`인지 확인한다.
- [x] 큐 대기/분배 단계의 응답이면 기존 분배룰로 처리한다.
- [x] 특정 내선 착신을 당겨 받는 현장 요구가 있으면 최소 대리응답 기능으로 분리한다.

**개발 계획:**

- [x] 최소 기능은 `같은 상담원 그룹 또는 같은 분배룰 소속` 조건으로 제한한다.
- [x] 통화 제어 API에 대리응답 요청 엔드포인트를 추가한다.
- [x] PBX 기능 코드 또는 AMI 제어 방식 중 운영 PBX에서 확실히 동작하는 방식을 선택한다.

**검증:**

- [x] 그룹 외 상담원이 대리응답하지 못하는지 확인한다.
- [x] 이미 응답된 호에 대한 중복 대리응답 요청이 실패하는지 확인한다.

### 11. 직통전화와 브랜치 그룹

**판단:** 기능 정의 확인 후 개발. 명칭만으로 구현하지 않는다.

**직통전화 확인 항목:**

- [ ] 수화기를 들면 자동으로 지정 대상에 발신하는 기능인지 확인한다.
- [ ] DID가 특정 상담원/분배룰로 직접 들어오는 기능인지 확인한다.
- [ ] 외부번호 단축 발신인지 확인한다.

**브랜치 그룹 확인 항목:**

- [ ] 지사 그룹인지, 전화기 단말의 pickup group인지 구분한다.
- [ ] CTI의 `branches`와 혼동하지 않도록 화면 명칭을 분리한다.

**개발 계획:**

- [ ] DID 직접 연결이면 기존 DID/분배룰 설정으로 흡수한다.
- [ ] 오프훅 자동 발신이면 후순위 단말 정책 기능으로 분류한다.
- [ ] pickup group이면 대리응답 기능과 함께 설계한다.

### 12. 시간별 동작

**판단:** 완료. 별도 지사 고급 탭을 새로 만들지 않고, 착신전환 조건의 다중 요일/시간대 설정으로 흡수한다.

**데이터 계획:**

- [x] DID 단위 업무시간 정책은 `asteriskForwardingRules.scheduleJson`에 저장한다.
- [x] 업무시간/점심시간/야간은 다중 시간대 착신전환으로 표현하고, 휴무는 공휴일 규칙이 우선한다.

**서버 계획:**

- [x] 착신전환 시간표는 `normalizeForwardingSchedules`와 렌더러의 스케줄 파서로 정규화한다.
- [x] PBX 렌더러는 `GotoIfTime`으로 현재 요일/시간에 따라 분기 가능한 설정을 생성한다.

**관리자 UI 계획:**

- [x] 착신전환 설정 모달에서 요일/시간대 여러 개를 등록할 수 있게 한다.

### 13. 공휴일 지정

**판단:** 추가 기능. 시간별 동작과 함께 개발하는 것이 적합하다.

**데이터 계획:**

- [x] `branchHolidayRules` 또는 `tenantHolidayRules` 테이블을 추가한다.
- [x] 반복 공휴일, 특정일 휴무, 임시 영업일을 구분한다.

**서버/UI 계획:**

- [x] 공휴일 캘린더 CRUD API를 추가한다.
- [x] 지사별로 테넌트 기본 공휴일을 상속하거나 재정의하게 한다.

**검증:**

- [x] 공휴일이 시간별 동작보다 우선 적용되는지 확인한다.

### 14. 국선 그룹

**판단:** 필요성 확인 후 개발. 국선별 설정이 가능한 현 구조에서 그룹은 다중 회선 풀/장애 우회/발신 라우팅이 있을 때만 의미가 있다.

**검토 기준:**

- [x] 동일 지사가 여러 국선을 묶어 발신해야 하는가: 현장 필요성 미확정.
- [x] 국선 장애 시 자동 우회가 필요한가: 현장 필요성 미확정.
- [x] 요금/통신사/지역별 발신 라우팅이 필요한가: 현장 필요성 미확정.

**개발 계획:**

- [x] 필요성이 확인되기 전에는 `trunkGroups`, `trunkGroupMembers` 테이블을 추가하지 않는다.
- [x] 지사/DID/발신 정책의 국선 그룹 선택 UI는 이번 마일스톤에서 보류한다.
- [x] PBX 렌더러의 그룹 우선순위와 fallback은 다중 국선 풀 요구가 확인될 때 별도 설계한다.

### 15. 후순위 전화기 부가 기능

**대상:** 내선별 단축 다이얼, 공동 단축 다이얼, 시간표시 방법, 서비스 등급표, 통화 그룹별 발신/응답 허용, 내선별 키버튼, 전화기 종류별 버튼, 다이얼번호 변경.

**판단:** 후순위. 대부분 단말 운용 또는 구형 PBX 관리 기능에 가깝고, 현재 CTI 운영 필수 기능으로 확인되지 않았다.

**계획:**

- [ ] 별도 백로그 문서에 보관한다.
- [ ] 실제 단말 모델, 프로비저닝 방식, 현장 운영 필요성이 확인된 항목만 개발 계획으로 승격한다.
- [ ] 서비스 등급표는 기존 PBX COS를 그대로 복제하지 않고 발신 제한, 국제전화 제한, 관리자 권한 같은 개별 정책으로 분해한다.

### 16. 시스템 재시동

**판단:** 별도 운영 기능. 설정 화면의 일반 기능으로 넣지 않는다.

**개발 계획:**

- [ ] 운영자 권한, 2단계 확인, 감사 로그가 있는 별도 시스템 운영 액션으로 설계한다.
- [ ] 초기에는 UI 버튼보다 운영 runbook과 관리자 API 보호 정책을 먼저 만든다.
- [ ] 재시동 대상은 CTI 서버, PBX 서버, 특정 서비스로 분리한다.

### 17. 내선/국선 포트 초기화

**판단:** 별도 장애 대응 기능. 어떤 포트를 왜 초기화하는지 정의 후 개발한다.

**확인 항목:**

- [ ] 통화 채널 강제 종료인지 확인한다.
- [ ] 단말 등록 해제/재등록 유도인지 확인한다.
- [ ] 특정 국선 회선 세션 초기화인지 확인한다.
- [ ] PBX 설정 DB 초기화 같은 위험 작업인지 확인한다.

**개발 계획:**

- [ ] 안전한 `통화 채널 정리`와 위험한 `설정 초기화`를 분리한다.
- [ ] 통화 중인 고객 영향이 있으므로 실행 전 영향 범위를 표시한다.
- [ ] 모든 실행은 감사 로그와 결과 상태를 남긴다.

## 번호 자원/기능 코드 계획

### 번호 자원

**역할:** 운영 정책과 충돌 검증.

- [ ] DID, 상담원 내선, 호 분배룰 내선, 기능 코드의 범위 충돌을 검증한다.
- [ ] 번호 자원 화면에서 번호를 클릭하면 해당 기능 설정 화면으로 이동할 수 있는지 확인한다.
- [ ] 즉시 이동이 가능한 경우 `resourceType`, `resourceId`, `targetRoute`를 응답에 포함한다.
- [ ] 단, 번호 자원이 기능 실행의 기준이 되지는 않는다.

### 기능 코드

**역할:** PBX 단말에서 특정 동작을 호출하는 코드.

- [ ] 대리응답, 착신전환 활성/해제, 내선 잠금 같은 기능 코드 후보를 별도 목록으로 관리한다.
- [ ] 관리자 화면에서는 기능 코드가 어떤 기능과 연결되는지 표시한다.
- [ ] 기능 코드 변경은 PBX 렌더러와 충돌 검증을 반드시 통과해야 한다.

## 테스트 계획

### 서버

- [ ] DTO 검증 테스트: DID/ARS/착신전환/분배 방식/내선 잠금.
- [ ] 서비스 테스트: 지사 착신 정책 저장, DID 중복 연결 방지, 분배 방식 매핑.
- [ ] PBX 렌더러 테스트: 큐 전략, DID 라우팅, 착신전환 시간표, 잠금 정책.
- [ ] 통화 제어 테스트: 내선 잠금 상태의 발신 차단.

### 관리자 앱

- [ ] 지사 편집 화면에서 DID/ARS/분배룰 선택이 깨지지 않는지 확인한다.
- [ ] 호 분배룰 생성/수정에서 외부 착신 방식 선택값이 API payload로 전달되는지 확인한다.
- [ ] 착신전환 모달에서 복수 시간표 저장/수정이 유지되는지 확인한다.
- [ ] 상담원 설정에서 내선 표시명/잠금 상태가 목록과 상세에 반영되는지 확인한다.
- [ ] 각 P0 설정 화면에서 도움말 아이콘이 표시되고, hover/focus/click/keyboard open 동작이 모두 동작하는지 확인한다.
- [ ] 도움말 패널이 기능 설명, 설정 방법, 운영 예시, 주의사항, 출처, 검토 상태를 누락 없이 표시하는지 확인한다.

### 통합 검증

- [ ] 설정 저장 후 PBX 설정 미리보기 결과가 바뀌는지 확인한다.
- [ ] 설정 변경 후 PBX 리로드 예약 또는 즉시 반영 경로가 의도대로 동작하는지 확인한다.
- [ ] 권한이 없는 상담원이 P0 설정 메뉴에 접근하지 못하는지 확인한다.
- [ ] 매뉴얼/엑셀/이미지/정보 검색 기반 도움말 생성 결과가 기능별 help key에 매핑되는지 확인한다.
- [ ] 출처가 없거나 검토되지 않은 자동 생성 도움말이 운영 화면에 노출되지 않는지 확인한다.

## 실행 순서

1. 완료된 M1/M2/M3 항목은 현재 코드 기준으로 유지보수 모드로 전환한다.
2. SMDR 외부 알림 세부 연동을 후속 작업으로 진행한다.
3. 직통전화와 브랜치 그룹은 현장 시나리오가 확정된 뒤에만 새 구현 계획으로 승격한다.

## 보류/결정 필요 항목

- [ ] 직통전화가 오프훅 자동 발신인지, DID 직접 착신인지, 단축 발신인지 확인 필요.
- [ ] 브랜치 그룹이 지사 그룹인지 pickup group인지 확인 필요.

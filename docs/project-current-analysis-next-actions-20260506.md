## 1. 현재 결론

현재 프로젝트는 P0, P1, P2의 코드 구현과 실행 가능한 리허설 검증을 대부분 마쳤고, 다음 단계는 P3 운영 전환 준비다.

가장 정확한 현재 단계는 다음과 같다.

- P0 운영 필수 계약, 통화 상태, PBX 설정 반영, 배포 리허설, 데스크톱 baseline 검증: 완료 또는 리허설 완료
- P1 관리자 운영 설정, 권한, IVR/멘트/테스트 표준화: 핵심 구현 완료
- P2 공지, 리포트, 운영 모니터링, PBX smoke gate: 2026-05-05 기준 완료 판정
- P3 운영 배포/릴리즈 안정화: 착수 대상

따라서 지금 해야 할 일은 새 기능을 넓히는 것이 아니라, 리허설에서 통과한 기능을 실제 운영 site 값, 실제 상담원 PC, 외부 알림 채널, 운영 보존 정책으로 묶어 운영 전환 게이트를 확정하는 것이다.

## 2. 전체 개발 계획

### 2.1 PBX 서버

Plan:

- DID 인입, 큐 분배, 상담원 내선, 착신전환, 녹취, IVR 입력, 수신거부, 블랙리스트를 운영 설정으로 관리한다.
- 관리자 앱에서 설정을 만들고, 반영 전 preview/diff/dry-run을 거쳐 PBX 서버에 반영한다.
- 반영 후에는 실제 smoke call과 CTI 상태 수집으로 결과를 확인한다.

현재상황:

- 설정 dry-run, preview, validation, reload, smoke gate가 리허설 site에서 통과했다.
- PBX 설정 owner guard가 추가되어 다른 서버가 공유 설정을 덮어쓰는 위험을 차단할 수 있다.
- queue + agent + WebSocket 조건의 one-command gate가 PASS 증적을 남겼다.

남은 핵심:

- 실제 운영 site 값으로 preflight를 실행한다.
- 운영 배포 중단 조건을 문서와 스크립트에 고정한다.
- 운영 PBX 설정 rollback 절차를 명확히 한다.

### 2.2 IVR

Plan:

- DID별 진입, DTMF 입력, timeout, 잘못된 입력, 수신거부, 문자 발송, 상담원 연결을 하나의 운영 흐름으로 관리한다.
- IVR 실패는 통화 이력과 리포트에서 원인별로 확인 가능해야 한다.

현재상황:

- DTMF 동작 규칙, 문자 템플릿, opt-out 연결, Smart ARS 이벤트 기반 실패 리포트가 구현됐다.
- 관리자 IVR 실패 리포트 API와 화면이 추가됐다.
- 기본 개발 서버에서 실패 원인 조회와 권한 라우팅을 검증했다.

남은 핵심:

- 운영 데이터 기준으로 실패 원인 분류가 충분한지 확인한다.
- 운영 피드백이 들어온 뒤 IVR 플로우 시각화 또는 추가 리포트를 별도 phase로 분리한다.

### 2.3 CTI 서버

Plan:

- PBX 이벤트를 통화 세션으로 조립하고, REST API와 WebSocket으로 상담원/관리자/데스크톱 앱에 같은 상태를 제공한다.
- command ack와 실제 통화 성공 판정을 분리한다.
- 멀티노드, 중복 이벤트, outbox, recovery timeout을 운영 안정성 기준으로 관리한다.

현재상황:

- 인증, 통화 세션, 통화 제어 상태, 이벤트 계약, outbox, recovery, 운영 monitoring API가 구현됐다.
- 서버 테스트 4개 suite, 37개 test와 서버 빌드가 통과했다.
- 리허설 smoke gate에서 DB, AMI event, WebSocket, 서버 로그 증적이 연결됐다.

남은 핵심:

- 운영 site별 DB migration 전후 절차를 확정한다.
- 장애 알림을 외부 채널로 발송하는 notification contract를 추가한다.
- 운영 데이터 보존/정리 정책을 코드 또는 runbook으로 연결한다.

### 2.4 상담원 웹 앱

Plan:

- 상담원 로그인, 상태 변경, 현재 통화, 고객 정보, 통화 제어, 후처리, 공지를 실제 서버 계약으로 동작시킨다.
- 웹 앱과 데스크톱 앱이 같은 통화 상태를 보게 한다.

현재상황:

- 공지사항 API가 상담원 화면 Full/Mini에 연결됐다.
- 통화 제어 상태는 서버 기준 이벤트를 따르도록 보정됐다.
- 기본 개발 서버에서 상담원 토큰으로 공지 API 응답을 확인했다.

남은 핵심:

- 운영 URL/CORS/WebSocket 설정으로 실제 배포 후 로그인, 공지, 통화 상태 갱신을 확인한다.
- 실제 상담원 PC에서 데스크톱 앱과 동시에 열었을 때 상태 정합성을 확인한다.

### 2.5 관리자 앱

Plan:

- 운영자가 지사, DID, 큐, 상담원, 권한, 착신전환, 멘트, 문자, 수신거부, 블랙리스트, 리포트, 모니터링을 관리한다.
- 화면 권한과 서버 권한이 어긋나지 않아야 한다.

현재상황:

- 공지, 리포트 고도화, IVR 실패, 녹취 다운로드 감사, 운영 모니터링 화면이 구현됐다.
- 관리자 앱 빌드가 통과했고, Vite chunk size warning은 있으나 빌드 실패는 아니다.
- 운영 모니터링 API는 outbox backlog, recovery count, WebSocket client 수, 알림 배열을 제공한다.

남은 핵심:

- 외부 장애 알림과 관리자 화면 알림 기준을 일치시킨다.
- 운영 배포 후 관리자 앱 routing, 권한 응답, 주요 리포트 조회를 smoke 항목에 포함한다.

### 2.6 Windows 데스크톱 앱

Plan:

- 실제 상담원 PC에서 pairing, SIP 등록, 수신, 발신, 종료, 오디오 장치, 업데이트를 검증한다.
- 장애 상황에서 웹 앱, 데스크톱 앱, CTI 서버 상태가 복구 가능한지 확인한다.

현재상황:

- 데스크톱 테스트 30개 파일, 123개 테스트가 통과했다.
- 프로덕션 빌드, unpacked package, process smoke, NSIS/portable 패키징이 통과했다.
- 서버-데스크톱 계약 테스트 5개 suite, 21개 테스트와 서버 빌드가 통과했다.

남은 핵심:

- 실제 Windows 상담원 PC, 헤드셋, 현장 네트워크에서 SIP 등록과 미디어를 검증한다.
- 통화 중 앱 재시작, 네트워크 단절, CTI 서버 재시작 복구 결과를 증적으로 남긴다.

### 2.7 테스트 앱

Plan:

- 배포 전후 동일한 PBX smoke/regression을 실행하고, 실패 위치를 PBX 서버, CTI 서버, WebSocket, DB, 테스트 입력값으로 분류한다.

현재상황:

- site별 테스트 값 분리, WebSocket capture, DB/AMI/log 증거 수집, PASS/FAIL 판정이 연결됐다.
- 최신 리허설 config apply gate는 Final verdict PASS다.

남은 핵심:

- 운영 site 값 파일을 추가한다.
- 배포 스크립트 또는 운영 runbook에서 smoke gate를 필수 단계로 호출한다.
- 실패 리포트가 운영 중단 판단으로 바로 이어지게 한다.

## 4. 앞으로 진행할 할일 목록

### 1순위: P3-1 운영 배포/릴리즈 안정화

목표:

- 운영 site 단위로 배포, migration, rollback, smoke gate를 반복 가능한 절차로 만든다.

할일:

1. 운영 site 이름, 서버 접속 기준, public URL을 확정한다.
2. 운영 DB, Redis, PBX, AMI endpoint와 credential 주입 방식을 확정한다.
3. `deploy/sites/_template` 기준으로 운영 site 디렉터리를 준비한다.
4. `scripts/deploy-prod.sh` preflight 항목을 운영 site 값 기준으로 점검한다.
5. DB migration 적용 전 백업, 적용, 검증, 실패 중단 기준을 문서화한다.
6. PBX 설정 owner guard를 배포 preflight에 포함한다.
7. 배포 후 health, Swagger, 관리자 앱, 상담원 앱, PBX smoke gate를 순서대로 실행한다.
8. 실패 시 rollback 기준과 이전 이미지/설정 복구 절차를 정리한다.

완료 기준:

- 운영 site 값만 바꾸면 같은 순서로 배포와 검증을 반복할 수 있다.
- migration 실패, health 실패, PBX 설정 owner 충돌, smoke 실패가 명확한 중단 조건으로 남는다.

### 2순위: P3-2 외부 알림 채널 연동

목표:

- 관리자 화면을 보고 있지 않아도 장애 발생과 복구를 받을 수 있게 한다.

할일:

1. 1차 알림 채널을 Slack, 이메일, SMS 중 하나로 확정한다.
2. 알림 credential 저장 방식과 운영 환경변수 이름을 정한다.
3. notification sink 인터페이스를 설계한다.
4. PBX AMI disconnect, DB 장애, Redis 장애, outbox backlog, RECOVERY_TIMEOUT 급증 알림을 정의한다.
5. 장애 발생 알림과 복구 알림의 조건을 분리한다.
6. 동일 장애 반복 알림 억제 기준을 추가한다.
7. 관리자 모니터링 화면의 알림 배열과 외부 알림 기준을 같은 규칙으로 맞춘다.

완료 기준:

- 외부 알림과 관리자 화면 알림이 같은 장애 기준을 사용한다.
- 장애 발생, 지속, 복구 상황이 중복 없이 전달된다.

### 3순위: P3-3 실 상담원 PC 현장 검증

목표:

- 실제 Windows 상담원 PC와 현장 네트워크에서 기본 상담 업무 흐름을 통과시킨다.

할일:

1. 실 PC 접근 가능 시간, 테스트 내선, DID, 헤드셋 정보를 확정한다.
2. `docs/qa/desktop-live-test-template.md`를 현장 기록지로 준비한다.
3. pairing과 SIP 등록 성공/실패를 검증한다.
4. 인입, 수신, 발신, 종료를 실제 PBX 서버와 확인한다.
5. 마이크, 스피커, 벨소리 장치 선택과 재시작 후 유지 여부를 확인한다.
6. 웹 앱과 데스크톱 앱을 동시에 열고 같은 통화 상태를 보는지 확인한다.
7. 통화 중 앱 재시작, 네트워크 단절, CTI 서버 재시작 복구 시나리오를 기록한다.

완료 기준:

- 실 PC에서 기본 상담 업무 흐름이 통과한다.
- 실패가 있으면 PC, 네트워크, 서버, 앱 중 어느 구간인지 증적으로 분리된다.

### 4순위: P3-4 운영 데이터 보존/정리 정책

목표:

- 감사와 장애 분석에 필요한 데이터는 보존하고, 운영 DB와 파일 저장소가 무기한 증가하지 않게 한다.

할일:

1. 녹취 다운로드 감사 로그 보관 기간을 확정한다. 현재 기준은 1년이다.
2. raw PBX event, event outbox, smoke report, 서버 로그 보관 기간을 정한다.
3. 운영 데이터와 테스트 데이터 정리 기준을 분리한다.
4. 수동 정리 runbook으로 둘지 scheduled job으로 구현할지 결정한다.
5. 정리 작업 전 백업 또는 export 필요 여부를 정한다.
6. 개인정보 마스킹과 감사 조회 권한 기준을 운영 문서에 반영한다.

완료 기준:

- 감사/장애 분석 데이터가 임의로 삭제되지 않는다.
- 오래된 테스트 데이터와 운영 로그가 통제된 방식으로 정리된다.

## 5. 지금 바로 필요한 입력값

P3를 실제로 착수하려면 다음 값이 필요하다.

- 운영 site 이름
- 운영 서버 접속 기준
- 운영 DB/Redis/PBX/AMI endpoint
- 관리자 앱 public URL
- 상담원 앱 public URL
- 외부 알림 채널과 credential
- 실 상담원 PC 접근 가능 시간
- 테스트 DID, 내선, 헤드셋/오디오 장치 정보
- rollback 허용 기준과 담당자

## 6. 실행 순서 제안

1. `P3-1 운영 배포 preflight 문서` 작성
2. 운영 site 값 수집 및 site 디렉터리 생성
3. staging 또는 운영 전환 대상에서 deploy dry-run 실행
4. DB migration precheck와 backup 절차 확인
5. PBX 설정 owner guard 확인
6. 운영형 배포 실행
7. health, Swagger, 관리자 앱, 상담원 앱, PBX smoke gate 순차 검증
8. 검증 리포트 저장
9. 외부 알림 채널 구현
10. 실 상담원 PC 현장 검증
11. 데이터 보존/정리 정책 확정

## 7. 보류할 항목

다음 항목은 P3 안정화 전에는 새로 확장하지 않는다.

- CRM/외부 시스템 신규 연동
- 관리자 리포트의 추가 UI 확장
- IVR 플로우 빌더 고도화
- 운영 PBX 값이 없는 상태의 production 설정 추정
- 대규모 UI 재구성

이 항목들은 운영 배포와 현장 검증이 안정화된 뒤 P4 또는 별도 phase로 분리한다.

# 테스터-퍼스트 서브에이전트 런처 (TDD 모드 · 선택)

> **전제:** 본 커맨드는 **Claude Code 전용** (CC5W 워크플로우). Agent 도구 필수.
> **선택 기능:** T-XXX 지시서 메타에 `tdd: true` 가 명시된 경우에만 호출. 기본 모드는 기존 `/tester`.

이 커맨드가 호출되면, 반드시 **Agent 도구**를 사용하여 독립 서브에이전트를 생성하라.
절대 현재 대화 컨텍스트에서 직접 테스트 작성 작업을 수행하지 마라.

**이유:** TDD 는 구현 컨텍스트가 있으면 "테스트가 구현을 따라가는" 편향(test-after disguised as test-first)이 발생한다. Agent 격리 + "코드 미존재 상태" 로 작성하여 Red-Green-Refactor 를 강제한다.

## 실행 절차

1. 프로젝트 루트 `CLAUDE.md`, `PLAN.md`, 해당 T-XXX 지시서를 읽어 대상 인터페이스 파악
2. 지시서에 `tdd: true` 명시 여부 확인. 없으면 중단하고 PM 에게 보고 (기본 `/tester` 경로 안내).
3. Agent 도구 호출 — 아래 프롬프트 템플릿으로 `{{CLAUDE_CONTENT}}` · `{{WORK_ORDER}}` · `{{INTERFACE_SIGNATURE}}` · `{{USER_INPUT}}` 치환
4. 산출: **실패하는 테스트 코드 파일** + 테스트 설계서 (메인 세션이 파일로 저장)
5. 사용자에게 보고 후 `/worker` 가 Green 을 만들도록 인계

## TDD 수칙 (엄격)
1. **Red 강제:** 테스트는 반드시 실행 시 실패해야 한다. 컴파일만 실패(빈 stub)도 허용하되, 의도적으로 경계/예외를 드러내는 assertion 을 포함하라.
2. **최소 테스트:** 1 테스트 = 1 명제. 여러 동작을 한 테스트에 묶지 마라.
3. **경계값 우선:** 빈 입력 · 최대 길이 · 0 · 음수 · null · 특수문자 등 경계를 정상 경로보다 먼저 설계.
4. **AAA 엄수:** Arrange / Act / Assert 3 블록 명시.
5. **의존성 분리 설계:** 실제 DB/파일/네트워크 호출 대신 fake/stub 경계 명확화. DI 인터페이스가 없으면 **PM 에게 "설계 조정 요청" 티켓 발행** (분석-아키텍처 Loop §1.6 (a) 아키텍처만 진입 가능성).
6. **금지:** 구현 코드 작성, Edit 을 통한 production 파일 수정. 테스트 파일 작성만 허용.

## 수행 절차
1. 대상 인터페이스에서 도출 가능한 명세 테스트 케이스 목록화
2. 경계/예외 케이스 3 개 이상 포함
3. tests/ 디렉토리에 테스트 파일 작성 (프로젝트 CLAUDE.md 지정 프레임워크)
4. 실행해 Red 확인 (`pytest -q` · `vitest run` · `go test ./...` 등 언어 표준)
5. 보고: Red 상태 스냅샷 + 테스트 파일 목록 + 남은 설계 공백 항목
